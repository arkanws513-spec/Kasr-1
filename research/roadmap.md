# خطة التنفيذ المرحلية

كل مرحلة لها مخرجات واختبارات قبول؛ لا ننتقل إلى التالية لمجرد أن الواجهة تبدو مكتملة.

## المرحلة 0 — التأسيس والبحث

**الحالة:** وثائق البحث والمعمارية قيد الإعداد.

- تثبيت حدود المشروع.
- توثيق المشاريع المرجعية والتراخيص.
- توثيق مخاطر التنفيذ الذاتي.
- تعريف مجموعة مهام أولية قابلة للتقييم.

**قبول:** وثائق واضحة، روابط مصادر، شجرة ملفات نظيفة، وسجل قرارات معماري.

## المرحلة 1 — نواة مهارات حتمية

- Skill Registry بإصدارات.
- إنشاء مهارة من قالب JSON/YAML موثق.
- تخزين واسترجاع SQLite.
- محرك تشغيل لعدد محدود من الإجراءات المسموحة.
- سجل تنفيذ قابل للفحص.

**قبول:** إضافة مهارة جديدة وتشغيلها مرتين، واسترجاع نفس الإصدار، وظهور سجل واضح دون نموذج لغة أو API خارجي.

## المرحلة 2 — تحقق مستقل

- معايير قبول لكل مهمة.
- مدقق منفصل عن منفذ المهمة.
- اختبارات ناجحة وفاشلة.
- حفظ الدليل بدل الاعتماد على تصريح الوكيل.
- تصنيف النتائج: passed / failed / inconclusive.

**قبول:** لا يمكن تسجيل المهارة «ناجحة» إلا بوجود تحقق قابل لإعادة التشغيل؛ لا يمر الفشل الصريح كنجاح.

## المرحلة 3 — التعلم من الخبرة

- استخراج درس مقترح من تجربة مكتملة.
- ربط كل درس بمصدره.
- تعزيز المهارة عند نجاحات متكررة مثبتة، وخفض ترتيبها عند الفشل.
- تجنب التكرار والتناقضات.
- دعم استعادة إصدار سابق.

**قبول:** تجربة فاشلة لا ترفع الثقة؛ تجربة ناجحة منفردة لا تتجاوز بوابة الاختبارات؛ كل تحديث قابل للمراجعة.

## المرحلة 4 — توليد بدائل وتحسين المهارات

- اقتراح مرشحين مختلفين للحل.
- تشغيلهم على مجموعة تدريب/تحقق ثابتة.
- قياس معدل النجاح، زمن التنفيذ، استهلاك الموارد، والأخطاء الجانبية.
- الاحتفاظ بأفضل مرشح وفق معيار محدد.
- اختبار الانحدار قبل الدمج.

**قبول:** يمكن إعادة التجربة من السجل؛ المرشح الأسوأ يُرفض تلقائيًا؛ النسخة المعتمدة لا تفقد الاختبارات السابقة.

## المرحلة 5 — واجهة ويب عملية

- واجهة عربية RTL وإنجليزية.
- قائمة المهارات وإصداراتها.
- إنشاء مهمة وتشغيلها وإيقافها.
- عرض خطوات التنفيذ والنتيجة والأدلة.
- شاشة للتجارب والمقارنة والموافقة.
- تصميم ملائم لشاشة الهاتف.

**قبول:** رحلة استخدام كاملة عبر متصفح الهاتف؛ أخطاء مفهومة؛ لا أسرار داخل الواجهة أو المستودع.

## المرحلة 6 — تكامل نموذج محلي

- Model Adapter مستقل.
- تشغيل checkpoint محلي من KASR-1 فقط عند توفره.
- اختبار اللغة والتخطيط واختيار المهارة.
- فصل بيانات التدريب والتحقق والاختبار.
- قياس جودة حقيقية، وعدم إظهار أن النموذج مدرّب إذا لم يكن كذلك.

**قبول:** حالة واضحة عند غياب الأوزان؛ لا ردود ثابتة متخفية كتوليد؛ اختبار smoke وقياس جودة موثق.

## المرحلة 7 — تدريب أوزان وتحسين مستمر مضبوط

- مراجعة تراخيص البيانات.
- تنظيف وتوثيق corpus.
- حفظ حالة optimizer والـ checkpoint.
- تدريب قابل للاستئناف.
- مقارنة النموذج السابق والجديد على اختبارات ثابتة.
- نشر checkpoint جديد فقط إذا اجتاز شروط القبول.

**قبول:** يمكن استعادة التدريب وإعادة التقييم، ولا يحدث تراجع غير موثق.

## أول مجموعة مهام مقترحة

1. تحويل CSV إلى JSON وفق schema مع اختبار الحقول.
2. تنظيم ملفات نصية داخل مجلد تجريبي.
3. إنشاء تقرير من بيانات اختبار صناعية.
4. اكتشاف خطأ مقصود في دالة Python داخل sandbox.
5. اقتراح تعديل للدالة، ثم تشغيل الاختبارات وإما قبوله أو رفضه.

تبدأ هذه المهام دون اتصال بنموذج مدفوع، وتثبت أن دورة التنفيذ والتقييم والتعلم تعمل فعلًا.
